# tars

Fedora 44 COSMIC Atomic as a bootable container image (`bootc`).

The `Containerfile` is plain: one pinned input and one floating one. The base image digest (`digests.txt`) is pinned. The layered RPMs (`packages.txt`) are names that float, and each build records what it got in `manifest.txt`. There is no third-party code in the build.

## Use

Run on the host. Needs `podman`, `skopeo`, `bootc` and `sudo` (all on Atomic already). Optionally `ln -s "$PWD/bin/tars" ~/.local/bin/tars`.

```sh
bin/tars              # list commands
bin/tars os           # list OS subcommands
bin/tars os bump      # move the base pin to the current digest of the tag
bin/tars os build     # build into root's container storage, write manifest.txt
bin/tars os deploy    # stage the rebuilt image (bootc upgrade; reboot to apply)
bin/tars os update    # bump + build + manifest diff, then offer to deploy
bin/tars os status    # show deployments
```

`tars git <args>` runs git in this repo from anywhere.

`tars` dispatches `tars <cmd>` to the `tars-<cmd>` script beside it, so new areas are new `tars-*` files.

Install stock Fedora COSMIC Atomic from the official ISO first. Then, **once per install**, move onto the image:

```sh
bin/tars os build
sudo bootc switch --transport containers-storage localhost/tars:44
```

Reboot. From then on, update with `tars os update` (or `bump`, `build`, `deploy` separately), and reboot. Roll back with `bootc rollback` or the boot menu.

## Notes

- **What is pinned, and what isn't.**
  - `digests.txt` is the base image digest, written by `tars os bump`. It fixes the base RPM set, *unless* a floating package forces an upgrade of a base one (e.g. `glibc-devel` needs a matching `glibc`); `tars os build` warns when that happens.
  - `packages.txt` is hand-edited: package *names*, one per line. They float: `tars os build` uses `--no-cache`, so every build takes the repos' current versions.
  - `manifest.txt` is generated by `tars os build`: every RPM in the built image, exact version. It is a record, never an input. Commit it so `git diff` shows what an update changed.
  - Exact RPM versions are not pinned by default: Fedora keeps only the latest build of each RPM, so such pins go stale within days. The base digest and the built image (with `bootc rollback`) are the reproducibility anchors.
- **To add a package**, add its name to `packages.txt` and run `tars os build`. Review the manifest diff.
- **To hold a package at an exact version** (say after a regression), write its full spec (`gcc-16.2.1-2.fc44`) in `packages.txt`, with a comment saying why. If the version leaves the repos, the build fails, which is what you want for a deliberate hold.
- **Why not BlueBuild?** It was tried and dropped. For a couple of packages it added third-party images pulled by tag, which run as root and ship in the OS, plus changes to the image (`/opt` rewiring, `/var` cleanup, a rewritten rpm-ostree base record). It would pay off with many of its modules.
- **Local storage for now.** `tars os deploy` runs `bootc upgrade`, which follows the image you're already on. Don't use `bootc switch` to pick up a rebuild: switching to the image you're already on is a no-op ("Image specification is unchanged"), even if the image behind the name changed. When this moves to GitHub, set `TARS_IMAGE=ghcr.io/<user>/tars:44`, build and push from Actions, and `bootc switch` to it once for normal `bootc upgrade`.
- **The base pin expires.** Fedora's dated tags are removed after about 4 weeks, so an old digest will eventually fail to pull. Run `tars os bump` (or `update`) at least that often.
- **Everything else should be an image.** Prefer `COPY --from=<pinned image>` for content that isn't a system toolchain.
- **Rust itself lives in `~/.rustup`**, pinned per project with `rust-toolchain.toml`. Link with mold via `~/.cargo/config.toml`.
- Kernel build tooling lives in toolbox, not in this image.
